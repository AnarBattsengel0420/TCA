\section*{Хураангуй}
\addcontentsline{toc}{section}{Хураангуй}

Энэхүү төгсөлтийн судалгааны ажлын зорилго нь интернэт холболтгүй сүлжээгүй орчинд компьютерын дотоод дискэнд хадгалагдсан баримт бичгүүдээс хиймэл оюун ухаанд суурилсан RAG (Retrieval-Augmented Generation) аргаар мэдээлэл хайх систем боловсруулах явдал юм.

Орчин үед мэдээлэл асар хурдтай өсч байгаа боловч байгууллагын дотоод мэдээллийг үр дүнтэй ашиглахад хүндрэл гардаг. Иймд энэхүү судалгаагаар дотоод орчинд ажиллах, өгөгдлийн аюулгүй байдлыг хамгаалсан хиймэл оюун ухааны хайлтын систем боловсруулах замаар уг асуудлыг шийдвэрлэхийг зорьсон.

Төслийн хүрээнд RAG архитектур ашигласан бөгөөд гурван хайлтын аргыг хослуулан ажилладаг: FAISS вектор хайлт (утгачилсан хайлт), BM25 статистик хайлт (түлхүүр үгээр хайлт), мөн шууд тохирол (үгийн тааруулалт). Бичвэрүүдийг Embedding загварт оруулж вектор буюу тоон массив болгон хувиргаж, ONNX INT8 форматаар өгөгдлийг боловсруулахад хурдан болгож CPU дээр хурдан ажиллах боломжийг хангасан. Хэрэглэгчийн интерфейсийг Gradio сан ашиглан вэб хэлбэрээр хэрэгжүүлсэн бөгөөд Ollama платформоор дамжуулан хэрэглэгчийн асуултанд тулгуурлан холбогдох баримтыг илрүүлэх ба LLM загвараас (Qwen2.5) хариулт үүсгэн авдаг.

Систем нь PDF, DOCX, CSV, XLSX, TXT зэрэг 10 төрлийн файлыг дэмждэг бөгөөд өгөгдлийн нууцлалыг бүрэн хангасан офлайн шийдэл юм.

\textit{Түлхүүр үг: RAG, FAISS, BM25, Hybrid хайлт, ONNX, офлайн AI, Ollama, Gradio}

\section{Удиртгал}

\subsection{Үндэслэл, ач холбогдол}

Орчин үед мэдээллийн хэмжээ хурдацтай өсч, байгууллага болон хувь хүний компьютерт олон төрлийн их хэмжээний өгөгдлийг богино хугацаанд боловсруулах, хайх, дүн шинжилгээ хийх шаардлага улам нэмэгдэж байна. Гэвч компьютерын дотоод дискэнд хадгалагдсан файлуудаас шаардлагатай мэдээллийг гараар хайх нь цаг их шаарддаг, алдаа гарах магадлал өндөр үйл явц юм.

APQC-ийн 2023 оны KM Benchmark судалгаагаар мэдлэгийн ажилтнууд ажлынхаа 20--30\%-ийг зөвхөн мэдээлэл хайх эсвэл дахин бүтээхэд зарцуулдаг бөгөөд энэ нь өдөрт дунджаар 1.8--2 цаг орчим юм. Хайлтын систем сайн ажилладаг байгууллагуудад энэ хугацааг 50\% хүртэл багасгаж чаддаг гэж тооцдог.

Мөн ихэнх RAG системүүд (ChatGPT, Perplexity гэх мэт) нь интернэт холболт шаарддаг тул байгууллагын нууц мэдээллийг гадаад серверт илгээх гэх мэт аюулгүй байдлын хувьд эрсдэлтэй. Иймээс бүрэн офлайн орчинд ажилладаг, өгөгдлийн нууцлалыг хамгаалсан RAG систем боловсруулах шаардлагатай гэж үзсэн.

\subsection{Зорилго, зорилт}

Энэ судалгааны зорилго нь компьютерын дотоод дискэнд хадгалагдсан бичвэрийн өгөгдлийг боловсруулан, хэррэглэгчийн асуултанд тохирох мэдээллийг автоматаар илрүүлж, холбогдох хариултыг гаргаж чаддаг RAG (Retrieval-Augmented Generation) технологид суурилсан хариултын системийг боловсруулан ажлын цаг хэмнэх, үр бүтээмжтэй байдллыг нэмэгдүүлэх юм.

Зорилт:

\begin{itemize}
    \item Локал дискнээс бичвэрийн төрлийн файл уншиж, вектор хэлбэрт хөрвүүлэх процессыг хэрэгжүүлэх
    \item FAISS вектор хайлт (утгачилсан хайлт), BM25 статистик хайлт (түлхүүр үгээр хайлт), мөн keyword matching (үгийн шууд тааруулалт) гэсэн гурван аргыг нэгтгэсэн Hybrid хайлт бүтээх
    \item Хэрэглэгчийн асуултанд үндэслэн утгачилсан хариулт үүсгэх LLM загвар ажлуулах
    \item ONNX INT8 оновчлол ашиглан индекс үүсгэх болон хайлтын процессыг CPU дээр хурдан ажиллах боломжтой болгох
    \item Хайлтын системийг туршиж оновчтой байдлыг нэмэгдүүлэх
    \item Gradio ашиглан хэрэглэгчид хялбар вэб интерфейс хэрэгжүүлэх
\end{itemize}

\subsection{Судалгааны хязгаарлалт}

Систем нь дотоод орчинд (сүлжээгүй орчинд) бүрэн ажилладаг. Гэвч дараах хязгаарлалттай:

\begin{itemize}
    \item Зөвхөн бичвэрт суурилсан файлуудыг дэмждэг — зураг, аудио, видео файл уншиж чадахгүй
    \item Зурган PDF (scan хийсэн) файлаас текст гаргахад OCR буюу тэмдэгт таних оптик технологийн шаардлагатай
    \item Локал LLM загварын хариултын чанар GPT-4 зэрэг том загвараас доогуур мөн англи хэлнээс бусад хэл дээр нарийвчлал багатай
    \item Монгол хэлний вектор загварын нарийвчлал хязгаарлагдмал (multilingual загвар ашиглаж байгаа)
    \item GPU байхгүй тохиолдолд вектор хийх хурд удаан байж болох бөгөөд энэ нь индекс үүсгэх болон хайлтын хурданд нөлөөлнө. Энэ системд CPU дээр тулгуурлан индекс үүсгэж байгаа тул хурд удаан байж болохыг анхаарах хэрэгтэй.
\end{itemize}

\subsection{RAG аргачлалын үндэс}

RAG (Retrieval-Augmented Generation) нь хайлт (retrieval) болон хэлний загварын үүсгэлт (generation)-ийг нэгтгэдэг аргачлал юм. Уламжлалт LLM загварууд зөвхөн сургалтын үеийн мэдлэгт тулгуурладаг бол RAG нь гадаад эх сурвалжаас мэдээлэл татан авч загварт контекст болгон өгдгөөрөө давуу талтай. Энэхүү зарчмыг \textit{``нэвтрэлт → хайлт → үүсгэлт''} гэсэн гурван үе шатаар тайлбарлаж болно.

\subsubsection*{3.1.1 Retriever бүрэлдэхүүн}

Retriever нь RAG-ийн ``хайлт'' хэсгийг хариуцдаг. Баримтыг векторт хөрвүүлж хадгалах ба асуулт ирэхэд хамгийн холбогдох хэсгүүдийг тодорхой алгоритмаар олдог. Retriever-ийн гол зарчим нь:

\begin{enumerate}
    \item \textbf{Indeksing үе} — Бичвэрүүдийг embedding загвараар тоон вектор болгон FAISS индексэд хадгална.
    \item \textbf{Query боловсруулах үе} — Хэрэглэгчийн асуултыг мөн адил вектор болгон хөрвүүлнэ.
    \item \textbf{Хайх үе} — Хоёр вектор хоорондын косинус зайгаар хамгийн ойрхон утгатай баримтыг олдог.
\end{enumerate}

Энэ системд Retriever-ийн доор гурван давхар дэд бүрэлдэхүүн оршдог — эдгээрийг §3.2-т нарийвчлан тайлбарлана.

% ────────────────────────────────
% 3.1.2  Generator — мөчир II
% ────────────────────────────────
\subsubsection*{3.1.2 Generator (LLM) бүрэлдэхүүн}

Generator нь Retriever-аас ирсэн контекст өгөгдөл дээр үндэслэн хүнд ойлгогдохуйц хариулт үүсгэдэг хэлний загвар юм. RAG технологид Generator нь шинэ мэдлэгийг LLM-ийн сургагдсан мэдлэгээс биш, харин Retriever-ийн өгсөн баримтаас уншдаг — энэ нь hallucination (буруу мэдээлэл зохиох) аюулыг эрс буурулдаг давуу тал юм.

Энэ системд Generator-ийн үүргийг Ollama платформ дээр ажиллах Qwen2.5 загвар гүйцэтгэдэг бөгөөд энэ талаар §4.8-т дэлгэрэнгүй тайлбарлана.

% ────────────────────────────────
% 3.1.3  Ажиллах дараалал
% ────────────────────────────────
\subsubsection*{3.1.3 Ажиллах ерөнхий дараалал}

\begin{enumerate}
    \item Баримт бичгүүдийг уншиж, chunk хэлбэрт хуваана
    \item Chunk бүрийг embedding загвараар тоон вектор болгон FAISS-д хадгална
    \item BM25 статистик индекс бүтээнэ
    \item Хэрэглэгч асуулт оруулахад гурван аргаар зэрэг хайна
    \item Хамгийн холбоотой Top-K chunk(ойролцоо мэдээлэл)-ийг LLM-д контекст болгон өгнө
    \item LLM хариулт үүсгэж хэрэглэгчид харуулна
\end{enumerate}

% ────────────────────────────────
% 3.2  Hybrid хайлт — мөчир I
% ────────────────────────────────
\subsection{Hybrid хайлтын онол}

Нэг хайлтын аргад найдах нь ерөнхий нөхцөлд хамгийн сайн үр дүн өгдөггүй: вектор хайлт утгачилсан асуултанд давуу ч яг нэг үгийн хайлтанд дутмаг, харин BM25 нь эсрэг зарчмаар ажилладаг. Иймд энэ систем гурван аргыг хослуулсан \textbf{Hybrid} буюу олон талт шийдлийг ашигласан.

% ────────────────────────────────
% 3.2.1  FAISS — мөчир II
% ────────────────────────────────
\subsubsection*{3.2.1 Вектор хайлт (FAISS)}

FAISS сан нь бичвэрийн утга, агуулгыг 384 хэмжээст тоон вектор болгон хувиргаж, косинусын томьёогоор векторуудын хоорондын зайг тооцоолон хамгийн ойролцоо утгатай баримтыг олдог. Үүний давуу тал нь ижил санааг өөр үгээр илэрхийлсэн баримтыг ч илрүүлэх боломжтой байдаг. Жишээлбэл, хэрэглэгч “ухаалаг гэрэлтүүлгийн систем” гэж хайлт хийхэд “автомат гэрэл удирдлагын технологи” гэсэн агуулгатай баримтыг мөн олж чадна.
FAISS индексийн хоёр горим:

\begin{itemize}
    \item \textbf{IndexFlatIP} — Бүх векторуудыг шууд харьцуулж, косинус төстэй байдлыг тооцоолон хамгийн ойролцоо утгатай хэсгийг олдог энгийн хайлтын арга. Өгөгдлийн хэмжээ бага үед (жишээ нь chunk $\le$ 5000) илүү тохиромжтой бөгөөд хайлт нь нарийвчлал өндөртэй байдаг.

    \item \textbf{IndexIVFFlat} — Векторуудыг эхлээд бүлэг (кластер) болгон хувааж, хайлт хийх үед зөвхөн хамгийн боломжит бүлгүүд дотор хайлт хийдэг арга. Энэ нь өгөгдлийн хэмжээ их үед (жишээ нь chunk $>$ 5000) хайлтыг илүү хурдан болгох давуу талтай.
\end{itemize}

% ────────────────────────────────
% 3.2.2  BM25 — мөчир II
% ────────────────────────────────
\subsubsection*{3.2.2 Статистик хайлт (BM25)}

BM25 (Best Matching 25) нь текст хайлтад ашиглагддаг алгоритм бөгөөд баримт бүрийг хэрэглэгчийн хайсан үгтэй хэр зэрэг тохирч байгаагаар нь оноогоор эрэмбэлдэг. Энэ алгоритм нь хоёр үндсэн хүчин зүйлд тулгуурладаг. Нэгдүгээрт, үгийн давтамж буюу хайсан үг тухайн баримт дотор хэдэн удаа давтагдсаныг тооцоолдог. Хэрэв тухайн үг олон удаа гарвал баримтын оноо нэмэгдэнэ. Хоёрдугаарт, баримтын урт буюу текстийн нийт үгийн тоог харгалзан үздэг. Урт баримтад үг олон удаа таарах магадлал өндөр байдаг тул алгоритм үүнийг жингээр тохируулж, хэт урт баримт давуу байдал авахгүй байхаар тооцоолол хийдэг. Ийм байдлаар үгийн давтамж болон баримтын уртыг хамтад нь тооцоолж, хэрэглэгчийн хайсан яг тухайн үгийг агуулсан баримтыг оноогоор эрэмбэлэн олдог. Тиймээс тодорхой түлхүүр үг дээр суурилсан хайлтад BM25 нь ихэвчлэн вектор хайлтаас илүү нарийвчлалтай ажиллах боломжтой.
BM25 оноог дараах томьёогоор тооцдог:

\[
  \text{BM25}(q,d) = \sum_{t \in q}
    \underbrace{\log\!\left(\frac{N - n_t + 0.5}{n_t + 0.5}+1\right)}_{\text{IDF}}
    \cdot
    \underbrace{\frac{f_{t,d}\,(k_1+1)}{f_{t,d} + k_1\!\left(1-b+b\,\frac{|d|}{\text{avgdl}}\right)}}_{\text{TF нормчлол}}
\]

Энд $N$ нийт баримтын тоо, $n_t$ тухайн үг агуулсан баримтын тоо, $f_{t,d}$ баримт $d$ дахь $t$ үгийн давтамж, $k_1=1.5$, $b=0.75$ нь тогтмол параметрүүд юм.

% ────────────────────────────────
% 3.2.3  Keyword matching — мөчир II
% ────────────────────────────────
\subsubsection*{3.2.3 Шууд тэмдэгтийн хайлт (Keyword Matching)}

Шууд тэмдэгтийн хайлт нь текст доторх үг, тэмдэгтүүдийг яг ижил дарааллаар нь харьцуулж таарч байгаа эсэхийг шалгах энгийн боловч үр дүнтэй арга юм. Энэ арга нь баримтын текстийг индексжүүлсний дараа хэрэглэгчийн оруулсан түлхүүр үгийг тухайн индекс дотор шууд хайж, яг ижил тэмдэгтийн дараалал таарах хэсгийг олдог.

Ийм төрлийн хайлт нь нэр, код, дугаар, тусгай нэр томьёо зэрэг яг ижил хэлбэрээр бичигдсэн мэдээллийг олоход илүү тохиромжтой. Учир нь вектор хайлт нь утгын ойролцоо байдлыг, BM25 алгоритм нь үгийн давтамжийг харгалзан баримтыг эрэмбэлдэг бол шууд тэмдэгтийн хайлт нь текст доторх тэмдэгтийн дарааллыг шууд харьцуулж шалгадаг. Иймээс ``CS101'', ``AB-203'', ``Node-RED'' зэрэг нарийн код, тусгай тэмдэгт агуулсан нэршлийг илрүүлэхэд энэ арга илүү найдвартай ажилладаг.
% ────────────────────────────────
% 3.2.4  Эцсийн нэгтгэл — мөчир II
% ────────────────────────────────
\subsubsection*{3.2.4 Гурван аргын эцсийн нэгтгэл}

Гурван аргын оноог нэгдсэн нийлбэрээр эцсийн оноо болгон тооцно:

\[
  \text{Score}_{\text{total}} =
    0.45 \times V_{\text{score}} +
    0.40 \times B_{\text{score}} +
    0.15 \times K_{\text{score}}
\]

Энд $V$ нь FAISS вектор оноо, $B$ нь BM25 оноо, $K$ нь түлхүүр үгийн оноо юм. Жингийн харьцааг хайлтын зорилгоос хамааран хэд хэдэн өөр тохиргоогоор (хайлтын горим) ашигладаг. Үүнд:
\textit{factual} (баримтад суурилсан хайлт),
\textit{semantic} (утга, санааны ойролцоо хайлт),
\textit{exact} (яг ижил түлхүүр үг таарах хайлт),
\textit{mixed} (дээрх аргуудыг хослуулсан хайлт) зэрэг багтана. 
Эдгээр хайлтын горимууд нь BM25, вектор хайлт болон түлхүүр үгийн хайлтын үр дүнд өгөх жинг өөр өөрөөр тохируулж, тухайн хэрэглээний шаардлагад тохирсон үр дүнг гаргахад ашиглагддаг.

\subsection{Ижил төрлийн судалгааны ажлуудын харьцуулалт}

\begin{enumerate}
    \item \textbf{Lewis et al.\ (2020)} — RAG-ийн анхны судалгаа. DPR + BART загвараар Wikipedia-аас хариулт үүсгэсэн~[1]. Гэвч бүх мэдээлэл онлайн Wikipedia-д суурилсан тул локал файлд хэрэглэх боломжгүй.

    \item \textbf{LangChain RetrievalQA} — LangChain framework-ийн бэлэн chain ашиглан баримт бичгээс хариулт үүсгэх~[5]. OpenAI API шаарддаг, офлайн орчинд ажиллуулахад нэмэлт тохиргоо хэрэгтэй.

    \item \textbf{PrivateGPT} — Бүрэн локал орчинд ажилладаг RAG систем. LlamaCPP + Qdrant ашигладаг~[12]. Гэхдээ зөвхөн PDF, TXT дэмждэг бөгөөд Hybrid хайлт (BM25+Vector) хэрэгжүүлээгүй.

    \item \textbf{Haystack (deepset)} — Модульчлагдсан NLP framework. ElasticSearch/FAISS retriever ашигладаг~[11]. Серверт суурилсан архитектур тул хэрэглэгчийн компьютерт ажиллуулахад хүнд.

    \item \textbf{Benedetti (2024/2025)} — GPT-3.5/4 ашиглан open-domain QA-д зориулсан RAG системийг RAGAS framework-оор үнэлсэн~[8]. API-based тул офлайн ашиглах боломжгүй.
\end{enumerate}

Дээрх харьцуулалтаас харахад ихэнх RAG систем нь нэг хайлтын арга, онлайн API, эсвэл цөөн файлын формат дэмждэг. Энэ систем нь \textbf{Hybrid хайлт (3 арга)}, \textbf{бүрэн сүлжээгүй орчинд}, \textbf{10 файлын формат унших}, \textbf{ONNX оновчлол буюу бага тооцоолол} хослуулсанаараа ялгаатай.

\subsection{Chunking (хэсэгчлэл)}

\subsubsection*{4.3.1 Ерөнхий зарчим}

Том файлуудыг жижиг хэсгүүдэд хуваах нь RAG системийн хайлтын нарийвчлалд шийдвэрлэх нөлөөтэй. Хэт том chunk нь холбогдохгүй мэдээллийг агуулж, хэт жижиг chunk нь утга алддаг.

\subsubsection*{4.3.2 Тохиргоо ба параметрүүд}

\begin{itemize}
    \item \textbf{Chunk хэмжээ:} 900 тэмдэгт — хэд хэдэн туршилтын дараа оновчилсон утга.
    \item \textbf{Давхцал (overlap):} 120 тэмдэгт — хэсгүүдийн хил дээрх мэдээлэл алдагдахаас хамгаална.
    \item \textbf{Хуваах цэг:} ``\textenglish{. }'', ``\textenglish{,\textbackslash n}'', ``\textenglish{\textbackslash n\textbackslash n}'' зэрэг байгалийн тасалдлаар хуваана.
\end{itemize}

\subsubsection*{4.3.3 Файл болон chunk хоорондын харилцаа}

Нэг файл олон chunk-т хуваагдах бөгөөд chunk тус бүрт эх файлын нэр болон зам хадгалагдана. Энэ нь хариулт үүсгэх үед эх сурвалжийн мэдээллийг дурдах боломжийг олгодог.

\subsection{FAISS вектор индекс}

\subsubsection*{4.5.1 Ерөнхий зарчим}

FAISS нь Facebook-ийн хөгжүүлсэн вектор хайлтын сан бөгөөд хэдэн сая вектор дундаас хамгийн ойрхон хөршийг хурдан олох зориулалттай. Систем нь chunk тоо 5000-аас доош бол шууд \textenglish{\texttt{IndexFlatIP}}, их бол \textenglish{\texttt{IndexIVFFlat}} ашигладаг.

\subsubsection*{4.5.2 IVF бүтэц}

\textenglish{\texttt{IndexIVFFlat}} нь векторуудыг $\sqrt{n}$ кластерт хуваадаг. Хайлтад бүх векторыг шалгахын оронд зөвхөн хамгийн ойр кластеруудыг шалгаснаар хурд эрс нэмэгддэг. \textenglish{\texttt{nprobe}} параметр нь шалгах кластерийн тоог тодорхойлно (6--24).

% ────────────────────────────────
% 4.6  Embedding кэш систем — мөчир I
% ────────────────────────────────
\subsection{Embedding кэш систем}

Системийг дахин ажиллуулах бүрт бүх файлыг дахин embedding хийх нь цаг их зарцуулдаг байсан. Энэ асуудлыг шийдэхийн тулд MD5 hash-д суурилсан кэш систем хэрэгжүүлсэн:

\begin{enumerate}
    \item Chunk бүрийн MD5 hash-ийг тооцоолно.
    \item Кэшт байвал хадгалагдсан embedding-ийг шууд ашиглана.
    \item Зөвхөн шинэ эсвэл өөрчлөгдсөн chunk-ийг дахин тооцоолно.
    \item \textenglish{\texttt{FileTracker}} класс нь файлын hash болон өөрчлөгдсөн хугацааг хадгалдаг.
\end{enumerate}

Энэ оновчлолын ачаар дахин индексэлэх хугацаа 614 секундээс ~5 секунд болж буурсан.

\subsection{Хөгжүүлэлтийн явцад тулгарсан хүндрэлүүд ба шийдлүүд}

Системийг хөгжүүлж турших явцад зөвхөн кодын синтаксийн алдаа биш, харин өгөгдөл боловсруулах арга болон системийн ажиллагааны урсгалтай холбоотой хэд хэдэн бодит хүндрэл гарсан. Доор хамгийн их тулгарсан асуудлуудыг тус бүрийн шийдлийн хамт тайлбарлав.

\subsubsection*{4.10.1 Chunking хэмжээ хангалтгүйгээс хайлтын үр дүн буурах}

\textbf{Асуудал:} Эхний хувилбар дээр том хэмжээтэй файлыг бүхэлд нь нэг embedding болгон хадгалж байсан. Баримтын тодорхой хэсэгт байрласан мэдээллийг хайлтаар олоход хүндрэл гарсан.

\textbf{Шийдэл:} Chunk хэмжээг 600-аас 900 тэмдэгт болгон нэмэгдүүлж, 120 тэмдэгтийн давхцал (overlap) нэмснээр хайлтын нарийвчлал мэдэгдэхүйц сайжирсан. Нийт chunk тоо 90,000-аас 60,862 болж буурч, боловсруулалтын хурд нэмэгдсэн.

\subsubsection*{4.10.2 FAISS индексийн хэмжээ зөрөх алдаа}

\textbf{Асуудал:} Embedding загварыг өөрчлөх үед өмнө үүсгэсэн FAISS индексийг ашиглахад ``dimension mismatch'' алдаа гарсан. Шинэ embedding-ийн хэмжээс хуучин индексийн хэмжээсээс өөр болсонтой холбоотой.

\textbf{Шийдэл:} Индексийг ачаалах үед хэмжээсийг шалгаж, зөрүү илэрвэл хуучин индексийг устган шинээр үүсгэдэг хамгаалалт нэмсэн.

\subsubsection*{4.10.3 PDF файлаас текст унших хүндрэл}

\textbf{Асуудал:} Зарим PDF файлаас текст бүрэн гарч ирэхгүй, эсвэл унших хугацаа удаашрах асуудал гарсан. Ялангуяа scan хэлбэрийн буюу зураг хэлбэртэй PDF дээр текст хэлбэрийн өгөгдлийг шууд олох боломжгүй байсан.

\textbf{Шийдэл:} §4.2.2-т тайлбарласан 4 шатлалт fallback механизмыг хэрэгжүүлснээр систем гацахгүй ажиллах болсон. Зурган PDF-ийг цаашид OCR-оор дэмжих хэрэгтэй гэж дүгнэсэн.

\subsubsection*{4.10.4 AI хариулт удаашрах асуудал}

\textbf{Асуудал:} Retriever-аас хэт олон текстийн хэсэг дамжуулах үед LLM хариулт үүсгэх хугацаа мэдэгдэхүйц өссөн. Офлайн орчинд CPU ашиглаж байсан тул энэ асуудал илүү мэдрэгдсэн.

\textbf{Шийдэл:} Зөвхөн хамгийн холбоотой Top-K chunk-ийг сонгож prompt-д оруулах байдлаар оновчлол хийсэн. Top-K-ийн өгөгдмөл утгыг 5 болгосон.

\subsubsection*{4.10.5 Дахин индексжүүлэх хугацаа их зарцуулах}

\textbf{Асуудал:} Системийг дахин ажиллуулах бүрт бүх файлыг дахин embedding хийж байсан нь хугацаа их зарцуулж байв.

\textbf{Шийдэл:} §4.6-т тайлбарласан MD5 hash-д суурилсан кэш системийг нэмснээр дахин ажиллуулах хугацаа 614 секундээс ~5 секунд болж буурсан.

\subsection{Дүгнэлт}

Энэхүү судалгааны ажлаар бүрэн офлайн орчинд ажилладаг Hybrid RAG систем амжилттай хэрэгжүүлсэн. Системийн гол давуу талууд:

\begin{enumerate}
    \item \textbf{Hybrid хайлт} — Вектор + BM25 + Keyword гурван аргыг хослуулснаар нэг аргад найдахаас илүү нарийвчлалтай үр дүн гардаг.
    \item \textbf{Бүрэн офлайн} — Интернэт холболт шаардахгүй, өгөгдлийн нууцлал бүрэн хангагдана.
    \item \textbf{Олон формат} — 10 төрлийн файл дэмждэг (PDF-д 4 шатлалт fallback).
    \item \textbf{Оновчлол} — ONNX INT8 + OpenVINO ашиглан GPU-гүй машин дээр 63 chunk/с хурдтай ажилладаг.
    \item \textbf{Масштаблаг} — 4000+ файл, 60,000+ chunk-ийг 700 секундэд индексэлж чаддаг.
    \item \textbf{Кэш систем} — Дахин индексэлэхэд зөвхөн өөрчлөгдсөн файлуудыг боловсруулна.
\end{enumerate}

Цаашид хөгжүүлэх боломжууд:

\begin{itemize}
    \item OCR нэмж зурган PDF-ийг дэмжих
    \item GPU хурдасгал (CUDA) бүрэн хэрэгжүүлэх
    \item Монгол хэлний тусгай embedding загвар сургах
    \item Олон хэрэглэгчийн горим нэмэх
\end{itemize}
